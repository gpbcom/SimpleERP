# T0.14: Platform service skeleton and image

**Status:** ✅ Done · **Ticket:** [TICKET.md](TICKET.md) · **Choices and trade-offs:** [IMPLEMENTATION.md](IMPLEMENTATION.md) · **Review:** [REVIEW.md](REVIEW.md)

## 🔭 What it does

- A new `platform` service, a regular FastAPI application that uvicorn serves from an application factory, with no command line.
- `GET /v1/health` answers `{"status": "ok"}` and is the only path served without a company.
- Every other request without a company is refused by the company-context middleware of T0.09.
- The service's own failures (unknown path, wrong method, invalid request, unexpected error) answer `application/problem+json` with a D122 code, and no exception text reaches the body.
- A two-stage image, built from the repository root, runs the service as a non-root user with a health check.

## ⚙️ How it works

1. **Start:** uvicorn calls `AppFactory.create` through `--factory`, in [`backend/services/platform/Dockerfile:30`](../../../backend/services/platform/Dockerfile#L30).
2. **Logging and configuration:** the factory configures logging from [`conf/logger.yaml`](../../../backend/services/platform/conf/logger.yaml), applies the `ERP_` environment overrides and validates `conf/app.yaml` into a `PlatformConfig`, in [`backend/services/platform/src/erp_platform/api/app_factory.py:56-59`](../../../backend/services/platform/src/erp_platform/api/app_factory.py#L56-L59). The defaults are in [`backend/services/platform/conf/app.yaml`](../../../backend/services/platform/conf/app.yaml).
3. **Build the application:** `AppBuilder.build` creates the `FastAPI` object and mounts the health router under `/v1`, in [`backend/services/platform/src/erp_platform/api/http/app_builder.py:82-84`](../../../backend/services/platform/src/erp_platform/api/http/app_builder.py#L82-L84).
4. **Problem handlers:** the builder loads the error catalogue through `ProblemService` and registers the handlers, in [`backend/services/platform/src/erp_platform/api/http/app_builder.py:85-86`](../../../backend/services/platform/src/erp_platform/api/http/app_builder.py#L85-L86). `ProblemHandler.register` covers HTTP errors, validation errors and any exception, in [`backend/services/platform/src/erp_platform/api/http/problem_handler.py:85-87`](../../../backend/services/platform/src/erp_platform/api/http/problem_handler.py#L85-L87).
5. **Company middleware:** the builder finds the refusal catalogue ([`app_builder.py:59-70`](../../../backend/services/platform/src/erp_platform/api/http/app_builder.py#L59-L70)), then adds `CompanyContextMiddleware` with `public_paths` from the configuration, in [`backend/services/platform/src/erp_platform/api/http/app_builder.py:87-94`](../../../backend/services/platform/src/erp_platform/api/http/app_builder.py#L87-L94). The middleware sits outside the exception handlers, so an unknown path without a company gets the context refusal, not a 404.
6. **A health call:** the route runs `HealthRouter.get_health`, which asks `HealthService.check`, in [`backend/services/platform/src/erp_platform/api/http/health_router.py:53-61`](../../../backend/services/platform/src/erp_platform/api/http/health_router.py#L53-L61) and [`backend/services/platform/src/erp_platform/service/health/health_service.py:31-38`](../../../backend/services/platform/src/erp_platform/service/health/health_service.py#L31-L38).
7. **A failure:** the handler picks a code (404 and 405 have their own, others `PLATFORM-INTERNAL-01`) and builds the body from the catalogue, in [`backend/services/platform/src/erp_platform/api/http/problem_handler.py:100-103`](../../../backend/services/platform/src/erp_platform/api/http/problem_handler.py#L100-L103). `ProblemService.problem` resolves the code and fills title, detail, status and code from the catalogue keys only, in [`backend/services/platform/src/erp_platform/service/problems/problem_service.py:55-64`](../../../backend/services/platform/src/erp_platform/service/problems/problem_service.py#L55-L64). An unexpected exception logs only its type, in [`backend/services/platform/src/erp_platform/api/http/problem_handler.py:128`](../../../backend/services/platform/src/erp_platform/api/http/problem_handler.py#L128).
8. **The catalogue file:** `ErrorCodeRepository.load` reads `conf/catalogs/error_codes.yaml` and raises its own error when it is unreadable, in [`backend/services/platform/src/erp_platform/storage/catalogs/error_code_repository.py:53-62`](../../../backend/services/platform/src/erp_platform/storage/catalogs/error_code_repository.py#L53-L62).
9. **The image:** the build stage runs `uv sync --locked --package platform --no-editable` ([`Dockerfile:15`](../../../backend/services/platform/Dockerfile#L15)); the runtime stage copies the venv, the service `conf/` and the shared refusal catalogue ([`Dockerfile:21-24`](../../../backend/services/platform/Dockerfile#L21-L24)), runs as user `simpleerp` and has a `HEALTHCHECK` on `/v1/health` ([`Dockerfile:26-29`](../../../backend/services/platform/Dockerfile#L26-L29)).

## 📝 Assumptions accepted

- The context middleware is the one of T0.09 (`erp_context`): the only one in the repository, and it implements REQ-T01-02 criterion 1.
- The package is named `erp_platform`, because `platform` would shadow the standard-library module. The uv package name stays `platform`.
- The health endpoint is `GET /v1/health` and answers `{"status": "ok"}`: the specifications name no path, so the most conservative choice.
- No budget is touched: `docs/specs/05-non-functional` sets no measure for a service skeleton.
- The roadmap's "factories" are the `AppFactory` of D406: the skeleton has no runnable, and AGENT.md requires factories only for runnables.
- K20, the `COPY` of `refusal_codes.yaml` into the image's `conf/catalogs/`: sound for this ticket, it changes only the Dockerfile and no lock, and the image test proves it.
