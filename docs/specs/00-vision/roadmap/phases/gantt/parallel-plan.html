How the harness runs tickets in parallel

TKT-16

One checkout, one shared branch

Every running ticket works in the main checkout on feature/tickets, its documents in docs/tickets/<ID>/. ticket_tree.py records each ticket's own files, and finish commits only those: one commit per ticket, the other tickets left uncommitted.

Start rule

Start when the prerequisites are done

At the gate of /ticket-run, tickets.py check refuses a ticket whose prerequisites are neither merged on origin/develop nor committed on feature/tickets, or a ticket that follows an external item before that item has happened. /ticket-run <ID> --force starts anyway, and logs why.

Conflicts

Lock areas

The same check refuses a ticket while an open ticket changes one of the same services, front ends or packages. The charts apply this rule: without it, even 6 lanes only finish in 85 days instead of 137 with 4, and you pay that back in merge conflicts.

TKT-15

A pull request per finish

After your code review, ticket_tree.py finish commits the ticket's own files on feature/tickets, pushes it and opens or updates its pull request, one Closes #<issue> per ticket. The automerge workflow merges it once every check passed.

Bottleneck

Your review

With 4 tickets at once you are busy 62 % of the time approving plans and reviewing, about 4 hours a day. More lanes add nothing. Reviewing line by line only the security-critical code (identity, tenant isolation, money), and the rest on its tests and screens, halves the review time, which brings 4 lanes to 107 days.

TKT-20

Issues, groups, board, budget

/issue-plan and /issue-run plan and run an issue with its child issues, or a group of issues, approved once, as fast as the start rule allows. The GitHub board, /board and the status line follow every ticket. How this was computed

  • Prerequisites were read from each ticket row of the 12 phase pages of docs/specs/00-vision/roadmap/phases/: what a ticket needs from another before it can be built and tested. There are 2523 links, judged from the text and kept in docs/specs/00-vision/roadmap/phases/gantt/ticket-graph.json. They are an estimate, to correct when a ticket is planned. python3 .claude/scripts/reports/roadmap_gantt.py build rebuilds this page and parallel-plan.md from it, with the tickets merged so far.
  • Durations come from the PROGRESS.md timings of the merged tickets. The merged tickets took 0 minutes of agent work on average. The model gives a medium ticket 48 minutes, to allow for later tickets being larger: small 0.7 h, medium 1.3 h and large 2.6 h in all, agent work first, then your time (approval and review).
  • Simulation: K lanes. A ticket holds its lane and its areas from its start until it is merged, and one person reviews tickets one after another. On the critical path, the ticket with the most work after it goes first.
  • External dates are the roadmap's, unchanged. Some can be brought forward because they are your own actions; others cannot, such as a partner's or a certification body's own schedule.
  • Not included: holidays, fix rounds beyond those already measured, and rework found at acceptance.
